## Plan: Complete the GitLab Community Agent Workflow

### Current implementation baseline

The first implementation pass added:

- Account-scoped connection settings, a fixed `gitlab` Host credential reference, sanitized Git-remote mapping plus project override, and durable SQLite records for inbox events, cursors, proposals, and issue workflows.
- A closed GitLab REST operation enum and a runner-side HTTPS mediator. The PAT stays in the runner vault; the mediator rejects arbitrary URLs/methods, redirects, unsafe resolved addresses, and echoed secrets. The host checks that the account's configured instance and workspace mapping are still current before dispatch.
- A GitLab tab alongside TRX, with setup, category selection, issue inbox, session prompts, per-proposal approval, draft-MR controls, review proposals, and discussion-to-session links.
- Basic mapping, deduplication, cursor, approval-state, diff-line, URL-policy, and adapter tests, plus a manual GitLab CE checklist in `docs/gitlab-agent-workflow.md`.

This is not yet the complete agent workflow. The current agent can receive ticket/comment context through Oqto UI prompts, but it does not have scoped GitLab tools. Draft MRs and review proposals are initiated by the UI. Polling is initiated by the GitLab pane and runs every minute only while that pane is mounted. The first-pass implementation and tests have not been compiled or run in the current environment because Cargo and Bun are unavailable.

### Agreed decisions from the interview (2026-11-05)

- **Placement and mapping:** first release is personal-workspace-only. An account has one GitLab instance and many mapped workspaces, but each workspace maps to exactly one GitLab project and a project cannot be mapped twice for the same account. Prefer a GitLab `origin` for mapping; if it is not an exact match or there are multiple candidates, ask the user. For pushes, use `origin` only when it matches the mapped project; otherwise ask which remote to use.
- **Instance URL and TLS:** support GitLab at the origin or under any-depth URL path prefix, but accept only bounded safe path segments. Reject userinfo, query/fragment, dot segments, encoded separators, and unsafe characters. Require HTTPS and the runner/system trust store; no per-instance CA upload or TLS bypass in v1.
- **Credential:** use the account’s personal PAT in Host credentials under ID `gitlab`, requiring GitLab `api` scope. Limit effective project access through that GitLab account’s memberships. Git pushes use the workspace’s normal Git authentication, not the Host PAT. After saving the instance, test the latest vault revision through `/user` before enabling polling. If the credential revision changes, test the new revision before using it.
- **Polling:** poll all mapped workspaces from a backend task. Use one deployment-wide environment setting, `OQTO_GITLAB_POLL_INTERVAL_SECONDS`, default `60`, valid range `60..=3600`; fail startup on an explicitly invalid value. Apply bounded concurrency and GitLab rate-limit/backoff handling. Enable assigned/authored issues and mentions/review requests by default; broad project activity is opt-in.
- **Event meaning:** issue mentions include `@username` in issue/MR descriptions and notes. Include all new non-system comments on tracked MRs. Deduplicate one entity update across categories and merge its category labels. Coalesce repeated unread updates; preserve read history. Mark an item read when the user opens it in GitLab or routes it to a session. Show global and per-workspace unread badges. Retain event content for 90 days; expire pending proposals after 30 days.
- **Issue adapter:** implement the shared Issues adapter alongside, not instead of, TRX; the GitLab board lists assigned/authored tickets and the activity inbox remains separate. Follow existing Issues-pane behavior: closed tickets are opt-in. Map GitLab open/closed state directly and use pre-created `oqto::ready`, `oqto::in_progress`, and `oqto::blocked` labels for intermediate states. No label means open. Use neutral priority and leave parent/blocker fields empty. Conflicting Oqto labels show a warning and are not auto-repaired. User-initiated status changes require an explicit proposal confirmation. Implementation-start approval also applies `oqto::in_progress`; block start if status labels conflict. Starting a closed issue requires a separate approved reopen proposal. Missing canonical labels block status writes until an administrator creates them.
- **Approvals and sessions:** agent tools may read only the ticket selected in the session and its linked MR. Ticket edits/status changes, issue comments, MR-thread replies, and inline reviews are proposals; draft-MR create/update is permitted only after implementation approval. If the bound session is deleted or no longer belongs to the workspace, let the user rebind the pending proposal and require approval again. At approval time, fetch current issue fields; show original/current/proposed values, preserve unrelated edits, and require explicit confirmation for every overwritten field.
- **Pi bridge:** use a new typed, session-bound Pi/runner-to-Oqto request/response path. The current `ExtensionControl` is frontend-to-extension and is not sufficient for agent-to-host calls. Never give Pi a bearer token. Agent operations derive account, workspace, mapping, host, and PAT from Oqto state and can create proposals but cannot approve them.
- **Merge requests and pushes:** track one MR per issue. Require a committed feature branch; never implicitly switch branches. On a draft-MR request, push the current branch using normal Git authentication, preferring a matching `origin`; report missing Git credentials or ask if another remote is needed. Never force-push without a separate confirmation. Default the target to the GitLab project's default branch; make any override visible in the draft. Include `Closes #<iid>`. A ready MR requires confirmation; moving a ready MR back to draft for an update also requires confirmation.
- **Reviews and discussions:** permit inline comments on any actual diff line; the agent selects the old/new side for context lines. Reject stale diff positions and ask the agent to refresh. Approve a whole review bundle once. If submission partially succeeds, persist accepted discussion IDs and resume only the remaining comments. For a new MR discussion routed to a session, the agent may draft a thread reply as a separately approved proposal; code work, normal push, and draft-MR create/update remain covered by implementation approval, while force-push and ready/re-draft transitions retain their separate confirmations.
- **Compatibility and tests:** target the current stable GitLab CE at release. Use mock REST/TLS fixtures for routine automated tests; no repository-managed Docker Compose GitLab. Defer a live disposable-CE workflow to release qualification. Use the system CA store for private TLS.

### Remaining gaps to close

1. **Pi extension and agent operations are missing.** `agent-instructions.md` only describes the UI workflow; there is no extension installed by the managed Pi extension pipeline, no agent-callable GitLab tool, and no complete binding from the active Pi session to the backend's scoped GitLab service. `ExtensionControl` is frontend-to-extension, so implement a typed reverse session-bound request/response instead of reusing it as-is.
2. **Polling is UI-lifetime-bound.** The server does not poll while users are away, coordinate concurrent poll requests, back off on API errors/rate limits, or publish durable inbox updates to other active UI sessions.
3. **Event selection and deduplication need refinement.** The `mentions_review_requests` category currently approximates requests with assigned MRs and does not discover issue/MR mentions or actual reviewer assignments. The same issue can appear under multiple enabled categories because deduplication currently includes category. API fetching is limited to one page; timestamp-only cursors can miss ties or pages.
4. **Inbox and tracker behavior is incomplete.** GitLab is represented as an inbox-specific pane rather than a full adapter matching the shared issue contract. Events do not have a read/acknowledge workflow or a clear unread notification count. Connection setup reports token readiness but does not validate the token against `/user` or show the authenticated GitLab identity.
5. **Agent-driven MR/review work is missing.** The UI asks the user to type the source branch, target branch, title, inline-comment path, line, and text. There is no agent operation to draft those artifacts, no agent-to-session Oqto operation for reading issues/discussions or creating proposals, and no automatic agent loop to address a new discussion and refresh its draft MR.
6. **Verification is incomplete.** No Cargo tests, frontend tests, typecheck, formatter check, or manual GitLab CE workflow ran. Existing tests do not yet exercise the full HTTP routes, a local TLS GitLab fixture, response redaction on the GitLab client, pagination/cursor boundaries, concurrent polling, or end-to-end approval transitions.
7. **Placement scope is not visible early enough.** The GitLab service rejects shared and remote-machine workspaces because the credential is account-owned on a personal runner. Keep v1 personal-only and disable/show the restriction in the UI before the user reaches an API error.
8. **Configured URL prefixes are not implemented yet.** The first pass accepts only a root origin and builds REST paths at `/api/v4`; extend the host/path policy and every operation builder for the agreed safe nested prefix without weakening redirect, TLS, or path-traversal protections.

### Decisions and security invariants

- Keep one configured GitLab instance per account and multiple project mappings. Do not introduce webhooks or multiple instances in this follow-up unless the user explicitly changes scope.
- GitLab access remains backend/runner mediated. The browser, prompts, tool arguments, extension configuration, and logs must never contain the GitLab PAT.
- Do not add a generic HTTP proxy or arbitrary URL/path/method tool. Agent tools must use a closed operation vocabulary and the active session's server-resolved workspace/project mapping.
- No agent write becomes effective without an Oqto approval record: implementation start, every ticket edit/comment, each MR-thread reply, inline-review submission, and changing a draft MR to ready or re-drafting a ready MR. After implementation approval, local code changes, normal pushes, and draft-MR create/update are allowed; force-push always needs separate confirmation.
- Treat a project remap or instance change as invalidating old cursors, linked MRs, pending proposals, and cached inbox state for the old project/instance. Keep approval transitions compare-and-set and retry-safe.
- Preserve local TRX behavior and keep GitLab personal-workspace-only in v1; expanding placement is a separate security design, not an implicit follow-up.

### Phase 1: Finish the scoped Pi tool bridge

1. Trace the existing `oqto-protocol::control::ControlOperation`, `agent_control` gateway, Pi extension command registration, and managed extension lifecycle. Add a typed reverse RPC bound to the active session; do not give Pi an HTTP bearer token or misapply the existing frontend-to-extension `ExtensionControl` direction.
2. Define bounded GitLab control operations for the minimal agent workflow: resolve active project, read the selected ticket/details, read its linked MR/current diff/discussions, propose issue/status-label edit or comment, propose implementation start, create/update a draft MR after approval, draft an inline review, and propose a reply in an existing MR discussion. Operations must not accept account ID, runner, host, credential ID, full URL, or raw HTTP method from the agent.
3. Bind every call to the authenticated user, session ID, and session workspace at the backend gateway. Resolve mapping and credentials from Oqto state on each call; reject mismatched sessions, stale mappings, unsupported placements, and oversized payloads.
4. Add a first-party Pi extension in Oqto's managed extension source, and include it in the default-extension reconciliation used by setup/deploy and new-user provisioning. The current installer syncs a pinned external extension tree and the default list is embedded by `oqto-usermgr`; add a reviewed first-party overlay and installer tests rather than assuming a local extension file is copied automatically. The extension should register typed tools, call the scoped Oqto operation bridge, present pending proposals as tool results, and never read or persist the GitLab token.
5. Require agent tool calls to create proposals for implementation start, ticket/status writes, issue comments, MR-thread replies, and inline reviews; a tool must never approve its own proposal. Permit draft-MR create/update only after implementation approval, with the push/branch safeguards in Phase 4. Do not expose a “ready” operation without the separate user confirmation.
6. Update `agent-instructions.md` to teach the real tool names/approval lifecycle after the extension is installed. Keep the existing UI as a visible fallback for configuration and approval.

### Phase 2: Make polling a backend service

1. Add a lifecycle-managed GitLab poll service that starts from Oqto state, stops cleanly on shutdown, and uses the existing SQLite pool and account runner authority. Do not create a detached task with an unbounded lifetime.
2. Poll enabled categories on `OQTO_GITLAB_POLL_INTERVAL_SECONDS` with the agreed 60-second default and 60–3600-second range. Fail startup if an explicitly configured value is malformed or out of range. Use per-account/project serialization, bounded concurrency, request deadlines, exponential backoff, and GitLab rate-limit handling. Keep UI refresh as an on-demand trigger that shares the same poll lock/cursor state.
3. Support assigned/authored issues, actual reviewer-requested MRs, `@username` mentions in descriptions/notes, opt-in broad project activity, and all new non-system discussions on tracked MRs. Verify REST filters against the current stable CE during release qualification; do not treat assignment alone as a review request.
4. Follow pagination safely. Persist a stable cursor that handles equal `updated_at` timestamps and page boundaries; advance only after all pages are stored. Deduplicate one entity update across categories and merge category labels; coalesce unread updates while retaining read history and 90-day content retention.
5. Add event read/acknowledge state and global plus per-workspace unread counts. Mark read when the user opens the GitLab item or routes it to a session. Publish user-scoped invalidation/count events through the existing WebSocket hub; keep the persisted inbox authoritative and never broadcast private project details to other accounts.
6. Keep discussion-to-session links restricted to the same account, workspace, project, issue, and tracked MR. Define behavior for deleted sessions, removed mappings, and closed/replaced MRs.

### Phase 3: Complete the ticket inbox and connection UX

1. Add a token-free **Test connection** operation using GitLab `/user` after saving the origin. Do not enable polling until it succeeds; allow retry after a missing/locked vault is fixed. Detect a changed vault revision and test it before further API use. Show authenticated identity and clear `connected`, `credential missing`, `vault locked`, and `instance unreachable` states without returning upstream secrets or raw error bodies.
2. Implement the shared issue-tracker port alongside TRX and the separate activity inbox. List assigned/authored issues, with closed issues opt-in; map native open/closed plus the agreed canonical labels; use neutral priority and empty parent/blocker fields. Keep TRX semantics unchanged.
3. Show remote-vs-override mapping source, allow changing/removing a mapping, enforce one mapping per `(account, workspace)` and prevent the same project being mapped twice per account, prefer matching `origin` or ask when remote mapping is ambiguous, and clearly restrict v1 to personal workspaces.
4. Make issue details available to the planning session (bounded description, labels, URL, and current status) and ensure the UI presents the full ticket context rather than only the truncated inbox summary.
5. Keep each write as a separately reviewable proposal with before/after fields, authoring session, project, ticket URL, creation time, and an idempotent decision state. Expire pending proposals after 30 days. Re-fetch issue fields at approval and show original/current/proposed values; preserve unrelated changes and require explicit confirmation for each overwrite. Surface failures as retryable only when safe; never silently replay a partially applied write.
6. Add tests for setup, remote mapping, override precedence, category preferences, read/unread inbox state, and the unchanged TRX pane.

### Phase 4: Complete agent-driven MR and review workflows

1. Let the agent inspect only the selected ticket, its linked MR/current diff/discussions, the current branch, and the project's default branch. Require a committed non-default feature branch. On a draft-MR request, perform a normal authenticated non-force push to matching `origin`; if `origin` does not match the mapping, ask for a remote. If Git auth is absent, fail with instructions; never substitute the API PAT. Force-push requires separate confirmation.
2. Make one-MR-per-ticket create/update idempotent. Default target to GitLab's project default branch, allow visible target overrides, and include `Closes #<iid>`. Verify the MR is already linked to the same issue before updating; handle pagination/source-branch lookup, duplicate requests, and unknown outcomes after timeouts. If a linked ready MR needs an update, confirm the ready→draft transition first.
3. Keep marking a draft ready behind a fresh user confirmation and an owned/tracked MR check.
4. Let the agent create an inline review proposal from the current MR diff. Bind the proposal to the precise diff version (base/start/head SHA), allow any actual diff line with an agent-selected side, validate every path/side/line again at approval, and reject stale positions so the agent must refresh.
5. Approve a full multi-comment review bundle once. Record each accepted discussion ID and resume only comments not yet submitted after partial failure.
6. When any new non-system discussion arrives on a tracked MR, let the user direct it to the linked session; let the agent draft a thread reply as a separate approval proposal. Code work, normal push, and draft-MR create/update follow the implementation approval; require separate confirmation for force-push and ready/re-draft transitions.
7. Add agent-tool tests proving callers cannot select another account/workspace/project, raw URL, token, or approval state.

### Phase 5: Verification and rollout

1. Install the repository-pinned Rust and Bun toolchains, then run `cargo fmt --check` and `cd backend && cargo test -p oqto`.
2. Extend backend tests for host parsing and private DNS/TLS, no redirects, fixed HTTP operation/method/path, nested token-echo redaction, credential revision changes, configuration/mapping races, cursor pagination/ties, event dedup across categories, approval CAS, and stale-diff/partial-review handling.
3. Run frontend tests including `tests/issues/oqto-ui-issues.test.tsx`, `tests/git/oqto-ui-git.test.tsx`, `tests/issues/gitlab-inbox.test.tsx`, and `tests/issues/gitlab-platform.test.ts`; then run `bun run typecheck:oqto-ui` and the repository's formatter/linter.
4. Use mocked REST/TLS fixtures for normal development tests. During release qualification, run `docs/gitlab-agent-workflow.md` against an operator-provided disposable project on the current stable GitLab CE; no repository-managed Compose instance is required. Verify success and rejection paths, including token rotation, connection host/path change, project remapping/duplicate mapping, pagination, duplicate polling, canceled approvals, rejected writes, normal/failed pushes, draft-MR retries, stale reviews, partial review resumption, and comment-to-session routing.
5. Document supported GitLab CE versions, required token scopes, TLS trust requirements for private CAs, personal-workspace-only scope (unless expanded), polling interval/rate behavior, and recovery after vault lock or credential rotation.

### Scope exclusions

- GitLab Duo, webhooks, multiple GitLab instances per account, generic GitLab URL proxying, and direct token access from a Pi extension remain out of scope.
- Do not claim implementation completion until the Pi extension, backend-owned polling, focused checks, and mock-fixture tests pass. Treat the live disposable-CE workflow as a release-qualification gate.
