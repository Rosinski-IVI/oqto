# GitLab Community workflow

Oqto supports one GitLab HTTPS instance (at the origin or under a safe nested URL prefix) per account, with multiple personal workspaces mapped to unique projects. Shared and remote-machine workspaces are not supported. Store a personal access token with the GitLab `api` scope in **Host credentials** using credential ID `gitlab`; Oqto tests `/user` before polling. The token is resolved on the personal runner and is never returned to the browser, Pi agent, prompts, or extension configuration. Disconnecting GitLab removes Oqto mappings and inbox data but leaves the vault entry intact; remove that credential separately if you want to revoke it locally.

The backend polls mapped workspaces even when the UI is closed. `OQTO_GITLAB_POLL_INTERVAL_SECONDS` defaults to 60 and accepts integer values from 60 through 3600. Assigned/authored issues and mentions/review requests are enabled by default; broad project activity is opt-in. Inbox content is retained for 90 days and pending proposals expire after 30 days. The shared workflow labels `oqto::ready`, `oqto::in_progress`, and `oqto::blocked` must already exist in each GitLab project before Oqto can write those statuses.

After selecting an issue in a session, Pi exposes the `oqto_gitlab` tool. Reads are scoped to that selected issue and its Oqto-linked MR. Tool writes create proposals only; users approve them in the Issues pane. Draft-MR creation/update requires implementation approval and pushes the current clean, committed feature branch using ordinary Git authentication. The GitLab API token is never used for Git transport. Force-push is not supported.

## Manual smoke test (disposable GitLab CE project)

1. Create a disposable GitLab CE project with one open issue, a default branch, and a private project access token with API scope.
2. In Oqto Host credentials, save that token under ID `gitlab` and unlock the vault. In the workspace Issues pane, select **GitLab**, enter the instance HTTPS origin, and map the workspace from its Git remote (or use the project-path override).
3. Configure notification categories and refresh the inbox. Verify assigned/authored/project activity appears once after repeated refreshes and that the GitLab token never appears in browser network responses or agent context.
4. Choose **Plan in session** and confirm the ticket text is sent to the active session without changing GitLab. Propose an implementation start and verify no implementation prompt is sent before approval; approve it and verify the prompt is sent to the same workspace session.
5. Propose a title/description edit and a comment. Verify each remains pending until individually approved, then check the issue in GitLab. Reject another proposal and verify it is not applied.
6. After implementation approval, create/update a draft MR from a committed, clean feature branch. Select a matching remote if origin does not match. Verify Oqto pushes without force, the MR uses GitLab's project default target unless overridden, contains a `Closes #<iid>` reference, and remains draft. Use **Mark draft ready…**, cancel the confirmation once, then confirm and verify GitLab changes it to ready. Confirm that updating a ready MR requires a separate confirmation to return it to draft.
7. Propose inline comments on added, deleted, and context lines using the old/new side. Approve the bundle once and verify discussions appear. Repeat with a stale diff; Oqto must reject the review before submission. Simulate a partial submission and verify retry resumes only comments whose discussion IDs were not recorded.
8. Add a new MR discussion comment in GitLab. Refresh the inbox and verify it is linked to the tracked issue/session. Choose **Address comment in session**, review the code, and update the draft MR; confirm the original comment remains a proposal until user approval where applicable.
9. Try configuring HTTP, an IP literal, a non-443 origin, encoded/dot path segments, and mapping a remote from a different host or path prefix. Each must be rejected. Confirm the GitLab API client follows no redirects and uses the system CA store for private HTTPS.
10. Verify the global/per-workspace unread badges, mark an item read by opening it or routing it into a session, and confirm the unread count changes. Rebind a proposal from a deleted session and verify it requires approval again.

Routine tests cover fixed operation construction, protocol rejection, SQLite persistence, and workflow helpers; a live HTTP/TLS fixture and this end-to-end checklist still need to run during release qualification against an operator-provided disposable GitLab CE project. Oqto does not ship a repository-managed GitLab Compose service. GitLab webhooks and multiple instances per account are out of scope.
